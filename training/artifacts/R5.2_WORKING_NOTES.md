## Task 2 — Why 51,120 grid cells collapse to 275 accepted (ROOT CAUSE CONFIRMED)

Evidence source: `kaggle_runs/train-dk-bridge/reports/.../corpus.json` (443 MB,
the run matching the user's notebook 346f4407, dated 15-Aug-2026). Reproduced
exactly: total=51,120 accepted=275 rejected=50,845 errors=0 (rate 0.54%).

Grid: 284 locations x 60 years (1966..2025) x 3 seasons = 51,120 cells.
Years inferred via `ObservationResolver.available_years()` = union of tabular
years (ICRISAT 1966-2017, data_season 2004-2019, DK_Features 2018-2023) AND
image catalog years (2018-2025). So the grid spans 60 years but satellite
imagery only exists for 2018-2025 (~8 years).

### Rejection issue-code counts (all real, from the corpus)
- ST-Q-IMG-001 (no image observations for season/year): 50,138 (98.1% of cells)
- ST-Q-TEMP-002 (0 observations; min 1): 50,138 (always co-occurs with IMG-001)
- ST-Q-TAB-001 (no exact tabular record matched): 20,291
- ST-Q-TEMP-001 / ST-TEMP-002 (temporal gap > 60d): 25 (all but one accepted)

### Rejection issue-combination buckets (rejected=50,845)
1. `(ST-Q-IMG-001, ST-Q-TEMP-002)` — 30,554 cells. Imagery missing entirely
   for that (location, year, season) -> no temporal observations.
   - Dominated by 1966-2017 (52 years x 852 cells/yr = 44,304 cells have NO
     imagery at all; those 44,304 all appear here or in bucket 2).
2. `(ST-Q-IMG-001, ST-Q-TAB-001, ST-Q-TEMP-002)` — 19,584 cells. No imagery AND
   no tabular record. Also all pre-2018 (ICRISAT-only years) mostly.
3. `(ST-Q-TAB-001)` alone — 706 cells. HAS imagery (982 cells have imagery
   overall) but tabular matching fails -> ST-Q-TAB-001. All 2018-2025.
4. `(ST-Q-TAB-001, ST-Q-TEMP-001, ST-TEMP-002)` — 1 cell (2019-05-12_EVI 2022).

Accepted buckets: 251 with no issues (score 100) + 24 with only gap warnings
(score 80). Accepted years ONLY 2018-2023 (imagery years with tabular), by
season Kharif=201, Zaid=45, Rabi=29. Accepted locations: Udupi, Dakshina
Kannada, Kodagu, Chikkamagaluru, Kasaragodu, plus DK taluk names and 4
raster-file-named pseudo-locations (e.g. `2019-05-27_EVI`, `2023-10-23_EVI`,
`2019-10-14_NDVI`, `2020-05-26_EVI`).

### Root cause summary
1. PRIMARY: The sampling grid is built over ALL years in the tabular+image
   catalogs (1966-2025, 60 years) but imagery only exists for 2018-2025.
   All 1966-2017 cells (44,304 = 86.7% of grid) are structurally unresolvable
   (no images -> no temporal observations -> ST-Q-IMG-001 + ST-Q-TEMP-002).
   This is a PLANNING problem, not a quality-gate defect.
2. SECONDARY: Within imagery years (2018-2025), only 982 cells have imagery,
   and only 275 of those also pass tabular (74 village-level data_season +
   201 district-level DK_Features). The 707 imagery-with-tabular-failure cells
   come from:
   - 2024/2025: 263 cells. Imagery exists but NO tabular table covers those
     years (data_season ends 2019, DK_Features ends 2023, ICRISAT ends 2017).
   - 2018-2019 data_season: 146 cells where no data_season row matches that
     (location,year,season) exactly -> fabricated record with matched_level
     "none" (matcher.py:263-269) -> rejected by ST-Q-TAB-001.
   - DK_Features district rows: 94 cells where the district-level record does
     not match the query district name -> fabricated -> rejected.
   - 467 cells with no tabular source at all (source_path=None).
3. NOT a quality-threshold issue: `fail_below=40` is never the binding
   constraint; every rejection carries at least one error/critical-severity
   issue (IMG-001 / TAB-001 / TEMP-002). No threshold loosening would help
   (those cells have no data).

### Cross-check vs earlier run
train-v6 corpus.json (11-Aug): total 51,122, accepted 74, rejected 51,046
(difference: 2 cells, likely different location sampling). Accepted 74 = all
data_season village-level, score 100 only. The dk-bridge run added 201
district-level accepted (DK_Features) -> 275.

## Task 4 — NaN instability (ROOT CAUSE + FIX APPLIED)

### Repro
`training/kaggle/scripts/repro_loss_finite.py` builds the real model (tabular
branch only — no raster locally) and runs the real MultiTaskLoss over every
accepted observation, plus reproduces the temporal split.

### Split composition (VERIFIED, temporal)
- train=187 (years 2018-2021), val=40 (2022), test=48 (2023).
- crop labels: 74/187 in train; 0 in val; 0 in test.
- yield present: 187/187, 40/40, 48/48.
- All 74 crop-labeled samples are data_season (2018-2019) -> land in train.
- val/test are ALL DK district-level samples -> no crop labels, IDENTICAL
  mean-filled tabular vectors, and yield targets all -0.4877 (near-constant).
  -> crop/support=0 on val/test; yield R2 = -78,019 is a NEAR-CONSTANT-TARGET
  artifact (ss_tot ~ 1e-9), NOT a model divergence. The model predicts the
  constant ~-0.489 and its absolute error is tiny (mae 0.0037).

### Finiteness (VERIFIED)
- tabular path finite for all 275 (7-dim, min=-2.978 max=6.0 on train);
- yield labels finite (train -0.4877..2.5917; val/test constant -0.4877);
- model forward + loss finite on every split (crop loss 0 on val/test because
  all targets are the -1 sentinel -> zero, yield loss 0.0569).
=> The NaN seen in the user's training log CANNOT come from the tabular+label
   path. It originates in the IMAGE branch (EfficientNetV2-S at 224px under
   fp16 AMP on Tesla P100) — consistent with "NaN detected; skipping step
   epoch=2 step=6" then val_loss NaN from ~epoch 6.

### Root-cause factors
1. `nan_policy: skip` (default) SILENTLY skipped NaN steps: trainer.py:452-468
   logged a warning, zeroed grads and continued. Run exited 0 with a best
   checkpoint chosen at epoch 11 despite NaN activity. NaN was being hidden.
2. fp16 AMP (`amp: true`, `amp_dtype: float16`) on P100 — classic overflow
   source for a 224px EfficientNetV2-S with near-constant 0.16/0.5 inputs.
3. `_nan_in_state` only checked the total loss + grads; no per-tensor record of
   WHICH tensor went NaN was captured, and the validator wrote NaN val_loss
   into history without any signal.

### Fix (small, targeted, applied + tested)
- `training/training/config.py`: default `nan_policy` changed `skip` -> `stop`.
- `training/config/training.yaml`: `nan_policy: skip` -> `stop`.
- `training/training/trainer.py`:
  - new `_collect_nan_diagnostics()` — on every NaN step records per-tensor
    NaN/Inf counts + min/max for the loss, per-task losses, inputs, targets,
    and the parameter names whose grads are non-finite;
  - new `Trainer.nan_steps` counter and `nan_diagnostics` list surfaced in
    `TrainingResult.summary()`;
  - with `stop`, the raised `TrainingRunError` carries the diagnostics detail.
- `training/training/validator.py`: Validator now accepts `nan_policy`; when
  `stop`, a NaN/Inf **validation loss** raises ValidationError instead of
  being silently logged. Per-metric NaN (e.g. R2 on constant targets) is
  intentionally NOT treated as a failure.
- Tests: `test_nan_policy_default_is_stop`, `test_nan_policy_stop_raises_with_diagnostics`
  added; full `training/training/tests` suite passes (158 tests).

### Residual (needs Kaggle GPU to confirm)
- Whether the image branch actually produces NaN on the real raster patches
  (needs the Kaggle mount + P100). The fail-loudly default + diagnostics will
  now surface the exact tensor the moment it happens.

## Task 9 — release metadata sources INF-DS-001 (ROOT CAUSE + FIX APPLIED + VERIFIED)

### Root cause
`package_sources.py` -> `persist_dataset_sources` -> `_resolve_db_path` looked
for `manager.metadata_db_path` / `manager.metadata_db`, but `DatasetManager`
NEVER exposed either. Result: `INF-DS-001` ("no metadata.db; generate metadata
first") fired on every release build EVEN when metadata.db existed on disk.
Because `persist_dataset_sources` is all-or-nothing, the failure cascaded:
no `location_index.parquet` -> `_persist_village_metadata` skipped -> release
package shipped without any of the 4 metadata artefacts (matches the stale
"Known issues" section in docs/releases/v2.0.0.md).

### Fix
- `training/dataset_manager/manager.py`: added public `metadata_db_path()`
  accessor (delegates to `settings.metadata_db_path()`).
- `training/inference/dataset_sources.py`: `_resolve_db_path` now resolves in
  priority order: manager API (`metadata_db_path`/`metadata_db`), then
  `settings.metadata_db_path()`, then `metadata_repository.db_path`; returns
  the first candidate that actually exists (fallback to first candidate path).
- New tests `training/inference/tests/test_dataset_sources.py` (6 tests):
  resolution via each path, `None` when absent, INF-DS-001 raised without a
  DB, and full 3-artefact persistence with correct columns.

### End-to-end verification against the shipped package
The `releases/v2.0.0/cropfusion_release-v2.0.0/` package (backfilled
15-Aug-2026, metadata timestamps 12:50) already contains all 4 metadata
files; `ReleasePackageLoader.load()` now succeeds (strict validation, all
sha256 checksums match). `metadata.db` holds feature_contract +
categorical_codes + backfill provenance (source: DK_Features raster grid +
data_season.csv). App-side `LocationResolver` reads the shipped
location_index (5,554 rows) / village_metadata / historical_context without
error.

### Remaining note

  state (missing metadata); now refreshed (Task 9 metadata note + Task 10

## Task 5/7 — yield-target scale consistency (VERIFIED DEFECT + DIAGNOSTICS ADDED)

### Evidence (real corpus + real LabelPipeline, `verify_yield_scale.py`)
- Raw yield by matched_level:
  - district (DK_Features) n=201: min 0.5314, max 1.5356, mean 0.9431
    (Yield_Proxy_NPP — a normalized NPP proxy, NOT kg/ha)
  - village (data_season) n=74: min 62, max 73730, mean 29507.4 (kg/ha)
  - Combined raw dynamic range: max/min = 1.39e5.
- Current scaler (fit on ALL 275, standard):
  mean=7940.86, scale=20481.18. Scaled by level:
  - district: ALL 201 samples -> -0.3877 (std=0.0, a single point)
  - village: -0.3847 .. 3.2122
- Only 14 DISTINCT scaled values across 275 samples (5.1% distinct ratio).
  -> the yield regression target carries NO signal for 73% of the corpus
     (the model just regresses DK samples to a constant).
- Alternative "fit on village-only" scaler: district still collapses to a
  single value (-0.9715). Scaling cannot fix the unit mismatch — the data
  must not mix units (or the proxy needs its own target/head).

### Why it matters
- Yield R2 on val/test (dk-bridge) = -78,019 / -143,128 is an artifact of
  near-constant standardized targets (ss_tot~0), NOT a model divergence.
- The loss is balanced by fixed weights (crop 0.75 / yield 0.25); a constant
  yield target inflates/deflates yield-task learnability unmeasurably.

### Fix (diagnostics, not silent behavior change)
- `training/preprocessing/label_pipeline.py`: `LabelPipeline.fit` now computes
  `yield_scale_stats` (n, min, max, mean, std, dynamic_range_ratio,
  scaled_distinct_values/ratio) and appends warnings when
  (a) raw dynamic range > 1e3 ("mixed units") or
  (b) scaled values collapse to <= max(2, n/10) distinct points.
  Surfaced via `LabelPipeline.summary()` (and Preprocessor.summary()).
- `training/kaggle/scripts/package_sources.py`: pipeline meta now records
  `yield_scale_stats` + warnings into sources.json.
- New script `training/kaggle/scripts/verify_yield_scale.py` -> report
  `training/artifacts/input_verification/yield_scale_report.json`.
- `training/kaggle/scripts/verify_model_input.py` now prints + records the
  yield-scale diagnostics.
- Tests: `test_yield_scale_diagnostics_flag_mixed_units`,
  `test_yield_scale_diagnostics_no_warning_clean_target`,
  `test_yield_scale_diagnostics_constant_collapse` (label pipeline). All
  preprocessing tests pass (92).

### Recommendation (deferred, requires data decision)
- Do NOT mix Yield_Proxy_NPP with kg/ha into one regression target. Options:
  (1) restrict yield regression to village-level kg/ha samples (74),
  (2) fit a separate scaler / head per matched_level,
  (3) scale the proxy onto kg/ha via a learned calibration.
  All change the training contract -> flag for the data team, not silently.

## Task 6 — temporal-split composition (VERIFIED + DIAGNOSTIC ADDED)

### Verified composition (real corpus + real splitter)
- Split config: temporal, ratios (0.7/0.15/0.15), no explicit test/val years.
- train n=187 (years 2018,2019,2020,2021) — crop_labeled=74 (all village
  data_season), yield_present=187, matched_levels {village:74, district:113},
  yield range 0.53..73730, yield_std 23942.7.
- val n=40 (2022) — crop_labeled=0, all district, yield std 0.3512, 5 distinct
  raw values (0.7077..1.5356) -> ALL standardized to ~-0.3875 (+/- 0.0001).
- test n=48 (2023) — crop_labeled=0, all district, yield 5 distinct values
  (0.6316..1.4232) -> ALL standardized ~-0.3876.
- Tabular input: train has 13 unique vectors / 187; val and test each have
  exactly 1 unique vector (all rows identical mean-filled).
- NO leakage: train/val/test years are disjoint.

### Consequences
- crop/support = 0 on val+test -> crop accuracy/precision undefined (matches
  the dk-bridge evaluation JSON).
- yield R2 = -78,019 (test) / -143,127 (val) is an artifact: standardized
  targets differ only in the 4th decimal (ss_tot ~ 1e-9), so R2 is numerically
  meaningless — NOT a sign of model divergence.
- The model's val/test input is a single constant tabular vector; the crop
  head receives all -1 sentinels (masked); yield regresses to ~-0.15 constant.

### Fix (surfaced, not silent)
- `training/preprocessing/dataset.py`: `split_observations` now runs
  `_diagnose_split_composition`, logging a WARNING for every degenerate
  holdout split: EMPTY, ZERO crop-labeled samples, single-constant yield, or
  yield collapse to <= max(2, n/10) distinct values.
- New tests in `training/preprocessing/tests/test_split.py` (6): flags
  zero-crop, constant yield, empty split, clean split has no issues, and the
  temporal-split warning fires via caplog.
- Confirmed firing on the real corpus via `repro_loss_finite.py`:
  "degenerate temporal split (val): val has ZERO crop-labeled samples...",
  "...(test): test has ZERO crop-labeled samples...", and the yield-collapse
  warning from Task 5/7.

### Assessment
The splitter itself is correct (no leakage). The defect is upstream: the
accepted corpus has only 74 crop-labeled samples, all in 2018-2019, and the
only 2022/2023 data is DK district-level (no crop labels, no real tabular
features). Any temporal split will produce val/test with zero crop support.
Fix = dataset-level (more crop-labeled years / district crop labels), not a
splitter change. Flag to data team; do NOT loosen the split.
